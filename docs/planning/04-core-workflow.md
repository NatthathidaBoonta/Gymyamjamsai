# Core System Workflow: Gymyamjamsai (ระบบติดตามพัฒนาการการออกกำลังกาย)

*(หมายเหตุ: โครงสร้างของเอกสารฉบับนี้ ได้ถูกนำมาปรับประยุกต์จาก "รูปแบบ Workflow การจัดการเรื่องร้องเรียน" ตามที่คุณระบุมา เพื่อให้เข้ากับบริบทของ "ระบบติดตามการออกกำลังกาย" ตาม Requirement FR-01 ถึง FR-10 อย่างสมบูรณ์)*

---

## 1. Workflow แบบลำดับขั้น (User Journey & System Process)
ครอบคลุมการทำงานตั้งแต่ผู้ใช้เข้ามาในระบบ จนถึงการวิเคราะห์และปรับตารางอัตโนมัติ

**Step 1: Onboarding & Data Collection (FR-01, FR-02)**
- ผู้ใช้เข้าสู่ระบบ/สมัครสมาชิก 
- ระบบบังคับให้ทำแบบประเมินและกรอกข้อมูลร่างกายเริ่มต้น (น้ำหนัก ส่วนสูง อายุ ระดับความฟิต) รวมถึงเป้าหมายหลัก

**Step 2: Plan Generation & Recommendation (FR-03, FR-04, FR-05)**
- ระบบนำข้อมูลมาประมวลผล (คำนวณ BMI, BMR ฯลฯ)
- ระบบดึงท่าออกกำลังกายจาก "คลังท่าออกกำลังกาย" (Exercise Library) ที่เหมาะสมกับระดับผู้ใช้
- ระบบสร้าง "ตารางออกกำลังกายอัตโนมัติ" สำหรับวงรอบแรก (เช่น แผนสำหรับ 2 สัปดาห์)

**Step 3: Active Execution & Logging (FR-06, FR-08)**
- ระบบส่ง "แจ้งเตือน/เตือนความจำ" ล่วงหน้า เมื่อถึงวันที่ผู้ใช้มีตารางออกกำลังกาย
- ผู้ใช้ดูคลังท่าทาง (วิดีโอ/รูปภาพ) ปฏิบัติตาม และกด "บันทึกผล" (เซต / ครั้ง / น้ำหนัก / เวลา) เข้าสู่ระบบ

**Step 4: Analytics & Feedback (FR-07)**
- ระบบนำผลการบันทึกรายวันมาพล็อตเป็นกราฟ/สถิติ
- ผู้ใช้สามารถดูสรุปพัฒนาการทางร่างกายของตนเองได้แบบ Real-time ผ่าน Dashboard

**Step 5: Smart Adjustment (FR-09)**
- เมื่อครบกำหนดการประเมินผล ระบบจะตรวจสอบพัฒนาการและประวัติการเข้าใช้งาน
- ระบบดำเนินการ "ปรับตารางอัตโนมัติ" (ให้หนักขึ้น เล็กลง หรือเปลี่ยนท่า) ตามความฟิตปัจจุบัน

**Step 6: Management & Override (FR-10)**
- Trainer หรือ Admin เข้ามาจัดการอัปเดตคลังเนื้อหา หรือเข้ามาแทรกแซงเพื่อปรับตารางให้ผู้ใช้แบบ Manual (กรณีผู้ใช้ต้องการคำแนะนำพิเศษ)

## 2. สถานะของแผนการออกกำลังกาย (Workout Lifecycle Status)
*(ประยุกต์จากสถานะการจัดการเรื่องร้องเรียน มาเป็นสถานะการดูแลผู้ใช้งาน)*

| สถานะ (Status) | คำอธิบายแต่ละสถานะ | ผู้รับผิดชอบ (Role) | เงื่อนไขการเปลี่ยนสถานะ (Transition Rules) |
| :--- | :--- | :--- | :--- |
| **1. Pending Profile** | ผู้ใช้สมัครสมาชิกแล้ว แต่ยังกรอกข้อมูลสุขภาพเริ่มต้นไม่ครบ | Member | **เปลี่ยนเมื่อ:** ผู้ใช้ทำแบบประเมินและกรอกเป้าหมายครบถ้วน |
| **2. Plan Generating** | ระบบกำลังประมวลผลเพื่อคำนวณและสร้างตารางออกกำลังกาย | System | **เปลี่ยนเมื่อ:** ระบบสร้างตารางเสร็จสิ้นและพร้อมใช้งาน (เปลี่ยนเป็น Active) |
| **3. Active Plan** | ตารางพร้อมใช้งาน ผู้ใช้อยู่ในช่วงที่ต้องปฏิบัติตามแผนและบันทึกผล | Member | **เปลี่ยนเมื่อ:** ผู้ใช้บันทึกผลครบตามวงรอบ (เช่น ครบ 1 สัปดาห์) หรือกดยกเลิกแผน |
| **4. Analyzing** | ระบบกำลังประเมินผลจากการบันทึกข้อมูลย้อนหลังเพื่อหาแนวโน้มพัฒนาการ | System | **เปลี่ยนเมื่อ:** ระบบประมวลผลเสร็จ และพบว่าต้องปรับเปลี่ยนตาราง |
| **5. Adjusted / Updated** | ตารางถูกปรับให้ยากขึ้นหรือง่ายขึ้นอัตโนมัติให้เข้ากับพัฒนาการใหม่ | System / Trainer | **เปลี่ยนเมื่อ:** ผู้ใช้ยืนยันการรับตารางใหม่ (กลับไปสถานะ Active) |

## 3. กรณีผิดปกติ (Edge Cases & Exceptions)
*(เทียบเคียงกับกรณี ข้อมูลไม่ครบ, ส่งผิด, เรื่องซ้ำ, หรือเกินกำหนด)*

1. **ข้อมูลไม่ครบถ้วน / ตัวเลขผิดปกติ (Incomplete / Invalid Profile):**
   - *ปัญหา:* ผู้ใช้กรอกค่าน้ำหนัก/ส่วนสูงผิดปกติมาก (เช่น น้ำหนัก 5 กก. ส่วนสูง 300 ซม.)
   - *การจัดการ:* ระบบ (System) จะหยุดอยู่ในสถานะ `Pending Profile` พร้อมแสดง Alert ให้ผู้ใช้แก้ไขค่าให้สมเหตุสมผล ก่อนที่ระบบจะคำนวณตารางให้

2. **ขาดการบันทึกผลเกินกำหนด (Skipped / Overdue Logs):**
   - *ปัญหา:* ผู้ใช้ไม่เข้ามาบันทึกผลการออกกำลังกายนานเกิน 7 วัน
   - *การจัดการ:* ระบบจะส่งแจ้งเตือน (FR-08) เพื่อกระตุ้น หากเกินกำหนดนานกว่านั้น ระบบจะ Freeze ตารางปัจจุบัน และเมื่อผู้ใช้กลับมา จะมี Popup ให้เลือกว่า "เริ่มวงรอบใหม่" หรือ "ทำต่อจากจุดเดิม"

3. **การบันทึกผลซ้ำซ้อนหรือพิมพ์ผิด (Duplicate / Outlier Entry):**
   - *ปัญหา:* ผู้ใช้กรอกข้อมูลซ้ำ หรือกรอกว่ายกน้ำหนัก 500 กก. (Typo)
   - *การจัดการ:* ระบบมี Data Validation ดักจับค่าที่เกินจริง (Outliers) และขึ้น Warning ให้ยืนยันก่อนเซฟลง Database

4. **พัฒนาการไม่คืบหน้า (No Progress Detection):**
   - *ปัญหา:* กราฟสถิติ (FR-07) ชี้ว่าน้ำหนักหรือความฟิตไม่เป็นไปตามเป้าเกิน 2 สัปดาห์
   - *การจัดการ:* ฟังก์ชัน Smart Adjustment (FR-09) จะปรับลดความยากของตารางลง 1 ระดับ และระบบจะแนะนำให้ Member ปรึกษา Trainer (ส่ง Request สื่อสารไปหา Trainer)

---
*ความต้องการด้าน Non-functional (Usability, Performance 2-3s, Responsive, Security PDPA, Availability 99%, Scalability, Maintainability) ถูกนำมาพิจารณาเป็นมาตรฐานในการออกแบบระบบทุกขั้นตอน (เช่น การดัก Data Validation ด้าน Security และการทำ Background Job เพื่อไม่ให้หน้าจอโหลดนานตอน Plan Generating)*
