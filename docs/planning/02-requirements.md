# Requirement Analysis: Gymyamjamsai

อ้างอิงจากเอกสาร `01-system-overview.md` และความต้องการเพิ่มเติมของระบบติดตามพัฒนาการการออกกำลังกายออนไลน์ (Gymyamjamsai)

---

## 1. วัตถุประสงค์ของระบบ
- เพื่อเป็นศูนย์กลางในการติดตามข้อมูลสุขภาพและพัฒนาการทางร่างกายของนักศึกษาและสมาชิกในรูปแบบออนไลน์
- เพื่อให้ผู้ใช้งานสามารถตั้งเป้าหมายสุขภาพ รับคำแนะนำตารางออกกำลังกาย และบันทึกผลได้อย่างเป็นระบบ
- เพื่อเพิ่มประสิทธิภาพในการบริหารจัดการกิจกรรมหรือคลาสออกกำลังกายของสาขาวิชา ตั้งแต่การสร้างกิจกรรมไปจนถึงการเช็คชื่อ
- เพื่อให้ผู้ดูแลระบบและอาจารย์มีข้อมูลเชิงสถิติ (Dashboard) สำหรับประเมินความสนใจและสุขภาพโดยรวมของผู้ใช้งาน

## 2. ปัญหาของระบบเดิม
*(สมมติฐานจากบริบททั่วไปที่มักพบในระบบที่ยังไม่ถูก Digitalized)*
- **การติดตามผลแบบกระจัดกระจาย:** ผู้ใช้ไม่มีเครื่องมือกลางในการบันทึกน้ำหนัก สัดส่วน และผลการออกกำลังกาย ทำให้ติดตามพัฒนาการได้ยากและขาดแรงจูงใจ
- **ความยุ่งยากในการลงทะเบียนกิจกรรม:** การจัดการคลาสหรือกิจกรรมของสาขาวิชาอาจใช้กระดาษ หรือฟอร์มออนไลน์ทั่วไป ทำให้ตรวจสอบจำนวนคนเต็มและเช็คชื่อได้ลำบาก
- **ไม่มีการประเมินผลอัตโนมัติ:** ไม่มีระบบช่วยวิเคราะห์ข้อมูลร่างกาย หรือแนะนำตารางออกกำลังกายเบื้องต้น ทำให้ผู้เริ่มต้นไม่รู้จะเริ่มอย่างไร
- **ขาดการสรุปผลและรายงาน:** การรวบรวมสถิติการใช้งาน หรือรายงานจำนวนผู้เข้าร่วมกิจกรรมเพื่อให้อาจารย์ดู ทำได้ยากและใช้เวลามาก

## 3. เป้าหมายของระบบใหม่
- **All-in-One Platform:** รวมระบบดูแลสุขภาพส่วนบุคคลและการลงทะเบียนกิจกรรมไว้ในที่เดียว ใช้งานง่ายผ่าน Web Application (Responsive)
- **Data-Driven Health & Visualization:** มีกราฟแสดงสถิติและสรุปพัฒนาการที่ชัดเจน เพื่อสร้างแรงบันดาลใจ (Gamification)
- **Automated Management:** ลดภาระงานของอาจารย์/ผู้ดูแล ในการจัดการผู้เข้าร่วมกิจกรรมและการสรุปรายงาน
- **Real-time Notifications:** มีระบบแจ้งเตือนเพื่อไม่ให้พลาดกิจกรรม หรือช่วยเตือนความจำในการออกกำลังกาย

## 4. Functional Requirements
**กลุ่ม Member / Student (สมาชิก/นักศึกษา):**
- **FR1:** ระบบต้องให้ผู้ใช้สมัครสมาชิก/เข้าสู่ระบบ และทำ Onboarding กรอกข้อมูลพื้นฐาน (อายุ, น้ำหนัก, ส่วนสูง, โรคประจำตัว, เป้าหมาย)
- **FR2:** ระบบต้องประมวลผลและสร้าง/แนะนำตารางออกกำลังกายที่เหมาะสมกับเป้าหมายเบื้องต้นได้
- **FR3:** ระบบต้องรองรับการบันทึกผลการออกกำลังกายแต่ละครั้ง (ประเภท, ระยะเวลา, น้ำหนักที่ยก, จำนวนครั้ง)
- **FR4:** ระบบต้องแสดงกราฟวิเคราะห์ข้อมูล และแสดงสรุปพัฒนาการ (น้ำหนัก, สัดส่วน, ความถี่) ทางหน้า Dashboard
- **FR5:** ระบบต้องสามารถปรับตารางออกกำลังกายให้อัตโนมัติ ตามความสม่ำเสมอและผลพัฒนาการของผู้ใช้
- **FR6:** ระบบต้องมีหน้ารายการกิจกรรม/คลาส ให้ผู้ใช้สามารถดูรายละเอียดและกดลงทะเบียนเข้าร่วมได้
- **FR7:** ระบบต้องรองรับการแจ้งเตือน (Notifications) เช่น กิจกรรมใกล้เริ่ม, เตือนการบันทึกผล หรือพัฒนาการถึงเป้าหมาย

**กลุ่ม Trainer / Teacher (ผู้สอน/อาจารย์):**
- **FR8:** ระบบต้องให้อาจารย์สร้าง แก้ไข ยกเลิก กิจกรรม/คลาสออกกำลังกาย พร้อมกำหนดจำนวนรับสมัครสูงสุดได้
- **FR9:** ระบบต้องแสดงรายชื่อนักศึกษาที่ลงทะเบียน และสามารถจัดการสถานะการเข้าร่วม (เช็คชื่อ) ได้
- **FR10:** ระบบต้องมี Dashboard สรุปจำนวนผู้ลงทะเบียนในกิจกรรมที่ตนเองดูแล

**กลุ่ม Administrator (ผู้ดูแลระบบ):**
- **FR11:** ระบบต้องให้แอดมินจัดการสิทธิ์ผู้ใช้งาน (CRUD Users) ได้
- **FR12:** ระบบต้องแสดง Dashboard สรุปภาพรวม (ผู้ใช้งานทั้งหมด, กิจกรรมยอดนิยม) และสรุปรายงานจำนวนผู้เข้าร่วมกิจกรรมได้

## 5. Non-functional Requirements
- **NFR1 (Performance):** ระบบต้องตอบสนองรวดเร็ว ใช้เวลาโหลดหน้าไม่เกิน 3 วินาที และรองรับการแย่งกันลงทะเบียนกิจกรรมได้โดยระบบไม่ล่ม
- **NFR2 (Usability):** UI/UX ต้องสวยงาม ใช้งานง่าย และรองรับการแสดงผลบนโทรศัพท์มือถือ (Responsive Web Design) เนื่องจากผู้ใช้อาจใช้งานขณะอยู่ที่ยิม
- **NFR3 (Security):** รหัสผ่านต้องถูกเข้ารหัส (Hash) ป้องกัน SQL Injection และจัดการ Authentication ผ่าน JWT Token อย่างรัดกุม
- **NFR4 (Deployment & Architecture):** ต้องใช้ Docker Compose สำหรับฝั่ง Dev และรองรับการ Deploy เป็น Single-container แบบ Multi-stage (Vite build + Express static) บน Railway

## 6. ข้อมูลที่ระบบต้องจัดเก็บ
- **User Data:** รหัสนักศึกษา, ชื่อ-นามสกุล, อีเมล, รหัสผ่าน (Hashed), Role, โรคประจำตัว, เป้าหมาย
- **Physical Logs:** ประวัติการเปลี่ยนแปลงน้ำหนัก, ส่วนสูง, ค่าที่คำนวณได้ (เช่น BMI), พร้อม Timestamp เพื่อพล็อตเป็นกราฟ
- **Workout/Exercise Library:** แคตตาล็อกท่าออกกำลังกาย, ประเภท (Cardio/Weight) และคำแนะนำ
- **Workout Logs:** ประวัติการออกกำลังกายรายวัน (ท่าที่เล่น, น้ำหนัก, จำนวนเซ็ต/ครั้ง, ระยะเวลา)
- **Activity Data:** ข้อมูลคลาสกิจกรรม (ชื่อ, รายละเอียด, เวลา, สถานที่, จำนวนที่รับ, ผู้สร้าง)
- **Registration & Attendance:** ข้อมูลการจองที่นั่งของนักศึกษา และสถานะการเช็คชื่อ
- **Notification Logs:** ข้อมูลประวัติการส่งการแจ้งเตือน (ข้อความ, วันเวลา, สถานะการอ่าน)

## 7. ข้อมูลที่ระบบต้องแสดงผล
- **Personal Dashboard (Member):**
  - กราฟเส้น (Line Chart) แสดงการเปลี่ยนแปลงของน้ำหนัก/สัดส่วน
  - แผนภูมิแท่ง (Bar Chart) สรุปความถี่ในการออกกำลังกายในสัปดาห์/เดือน
  - กล่องแจ้งเตือนรายการกิจกรรมที่กำลังจะถึง
- **Activity Board:** หน้ารายการกิจกรรม พร้อมแถบ Progress Bar แสดงสถานะจำนวนผู้ลงทะเบียน (เช่น 15/20 คน)
- **Admin/Teacher Dashboard:** ตัวเลขสรุปผู้ใช้งาน, กราฟแนวโน้มความสนใจในกิจกรรมต่างๆ, และตารางข้อมูลดิบ (Table) สำหรับ Export

## 8. เงื่อนไขทางธุรกิจของระบบ (Business Rules)
- **BR1:** นักศึกษา 1 คน ไม่สามารถลงทะเบียนกิจกรรมที่เวลาชนกันได้
- **BR2:** เมื่อคนลงทะเบียนกิจกรรมเต็มจำนวน ระบบจะเปลี่ยนปุ่มเป็น "เต็มแล้ว" และไม่อนุญาตให้ลงทะเบียนเพิ่ม
- **BR3:** ข้อมูลน้ำหนักและประวัติการออกกำลังกายเป็นข้อมูลส่วนบุคคล จะแสดงให้ผู้ใช้อื่นเห็นไม่ได้ ยกเว้นแอดมินหรืออาจารย์ที่ดูแล (ในรูปแบบภาพรวมที่ไม่ระบุตัวตน หรือได้รับอนุญาต)
- **BR4:** ระบบจะคำนวณเพื่อปรับตารางออกกำลังกายอัตโนมัติ (Smart Plan) เมื่อครบรอบกำหนด (เช่น ทุก 7 วัน หรือ 14 วัน)

## 9. ข้อจำกัดและข้อควรระวัง
- **การ Deploy (Railway Single-container):** ต้องระวังการทำ Routing เพราะ Frontend (React) ทำงานแบบ SPA หากใช้ Express Serve ต้องตั้งค่า Catch-all route (res.sendFile) ให้ถูกต้องเพื่อไม่ให้เกิดปัญหา 404 เมื่อ Refresh หน้า
- **Data Privacy:** ข้อมูลสุขภาพมีความอ่อนไหว ต้องแน่ใจว่าไม่มีการ API Leak
- **User Entry Friction:** การบันทึกผลออกกำลังกาย หากต้องกรอกหลายช่อง อาจทำให้ผู้ใช้ขี้เกียจบันทึก ควรออกแบบ UI การกรอกข้อมูล (Daily Logging) ให้กดง่ายและเร็วที่สุด

## 10. คำถามที่ควรถามผู้ใช้งานจริงเพิ่มเติม
1. **ตรรกะการปรับตารางอัตโนมัติ:** มีสูตรเฉพาะสำหรับการประมวลผลสร้างและปรับตารางอัตโนมัติหรือไม่? หรือให้ระบบทำเพียงแนะนำจาก Template ที่เตรียมไว้?
2. **ระบบแจ้งเตือน (Notifications):** การแจ้งเตือนในระบบ (In-app Notification) เพียงพอหรือไม่? หรือต้องการให้ส่งแจ้งเตือนผ่าน Email / LINE Messaging API ด้วย?
3. **ระบบการจองกิจกรรม:** ในกรณีที่กิจกรรมเต็ม จำเป็นต้องมีระบบเข้าคิวสำรอง (Waiting List) หรือไม่?
4. **การเช็คชื่อเข้ากิจกรรม:** อาจารย์ต้องการเช็คชื่อด้วยการติ๊กในระบบ หรือต้องการให้มี QR Code เพื่อให้นักศึกษาสแกนเพื่อเช็คชื่อตัวเอง?
