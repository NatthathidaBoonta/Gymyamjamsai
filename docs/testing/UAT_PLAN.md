# User Acceptance Testing (UAT) Plan: Gymyamjamsai

เอกสารฉบับนี้คือ **แผนการทดสอบการยอมรับของผู้ใช้ (UAT Plan)** สำหรับระบบติดตามการออกกำลังกาย Gymyamjamsai เพื่อให้ผู้ใช้งานจริงในแต่ละกลุ่ม (Role) ได้ทดลองใช้งานระบบและยืนยันว่าระบบตอบสนองความต้องการและสามารถทำงานได้จริงในสภาวะแวดล้อมจำลอง (Staging/Production-replica)

---

## 1. UAT Objectives (วัตถุประสงค์ของการทดสอบ)
- เพื่อยืนยันว่าระบบสามารถทำงานได้จริงตาม Business Workflow ตั้งแต่ต้นจนจบ
- เพื่อให้มั่นใจว่าหน้าจอและการใช้งาน (UX/UI) ใช้งานง่าย ไม่ซับซ้อนสำหรับบุคคลทั่วไป
- เพื่อตรวจหาข้อผิดพลาดทางตรรกะ (Logical Errors) ที่อาจหลุดรอดมาจากการทดสอบของนักพัฒนา
- เพื่อให้ตัวแทนผู้ใช้งานลงนามยอมรับ (Sign-off) เพื่อเปิดใช้งานระบบจริง

## 2. UAT Scope (ขอบเขตการทดสอบ)
**รวมถึง (In-Scope):**
- ฟังก์ชันการสมัครสมาชิกและการเข้าสู่ระบบ
- ฟังก์ชันสำหรับ "สมาชิก (Member)": การจัดตารางออกกำลังกาย, การจองคลาสกิจกรรม, การดูพัฒนาการตนเอง
- ฟังก์ชันสำหรับ "เทรนเนอร์ (Trainer)": การสร้างคลาสกิจกรรม, การเช็คชื่อผู้เข้าร่วม
- ฟังก์ชันสำหรับ "ผู้ดูแลระบบ (Admin)": การดูภาพรวมของฟิตเนส, การจัดการผู้ใช้งานและท่าออกกำลังกาย
- การแสดงผลบนคอมพิวเตอร์และโทรศัพท์มือถือ

**ไม่รวมถึง (Out-of-Scope):**
- การทดสอบเจาะระบบ (Penetration Testing)
- การทดสอบรับโหลดสูง (Stress/Performance Testing)

---

## 3. UAT Users / Roles (กลุ่มผู้ทดสอบ)
| Role ในระบบ | ตัวแทนผู้ทดสอบ (UAT Testers) | หน้าที่หลักในการทดสอบ |
| :--- | :--- | :--- |
| **Member** | สมาชิกฟิตเนส / ลูกค้าทั่วไป | เน้นทดสอบการสมัคร, การจองคลาส, และหน้าต่างสรุปการออกกำลังกาย |
| **Trainer** | เจ้าหน้าที่ฟิตเนส / เทรนเนอร์ | เน้นทดสอบการเปิดคลาสใหม่, การเช็คชื่อ, และการจัดการกิจกรรม |
| **Admin** | ผู้บริหาร / ผู้จัดการฟิตเนส | เน้นดูสถิติภาพรวมบน Dashboard, Export รายงาน, และการจัดการข้อมูลพื้นฐาน |

---

## 4. Test Scenarios by Role (สถานการณ์จำลองสำหรับการทดสอบ)

### 4.1. สถานการณ์ของ Member (สมาชิก)
- **SC-M01:** สมัครสมาชิกใหม่สำเร็จ และสามารถ Login เข้าสู่ระบบได้
- **SC-M02:** เข้าไปหน้าตารางกิจกรรม เลือกจองคลาสที่สนใจ (ระบบต้องแจ้งเตือนความสำเร็จ)
- **SC-M03:** ลองจองคลาสที่เวลา "ทับซ้อนกัน" (ระบบต้องป้องกันและแจ้งเตือนว่าเวลาชนกัน)
- **SC-M04:** เข้าไปอัปเดตน้ำหนักเป้าหมายของตนเองที่หน้า Profile
- **SC-M05:** เข้าดูหน้า Dashboard ของตนเอง กราฟสถิติต้องแสดงข้อมูลได้

### 4.2. สถานการณ์ของ Trainer (เจ้าหน้าที่ฟิตเนส)
- **SC-T01:** สร้างกิจกรรม (คลาสออกกำลังกาย) ใหม่ โดยระบุวันเวลา และจำนวนที่นั่ง
- **SC-T02:** ลองสร้างกิจกรรมโดยใส่จำนวนที่นั่ง "ติดลบ" (ระบบต้องบล็อกไม่ให้สร้าง)
- **SC-T03:** เข้าไปเช็คชื่อ (Attendance) ผู้เข้าร่วมกิจกรรมเมื่อถึงเวลาคลาสเรียน

### 4.3. สถานการณ์ของ Admin (ผู้บริหาร)
- **SC-A01:** เข้าดูหน้า Admin Dashboard เพื่อดูสถิติจำนวนผู้ใช้งานและจำนวนกิจกรรมทั้งหมด
- **SC-A02:** เข้าหน้า Exercises เพิ่มท่าออกกำลังกายใหม่เข้าสู่คลัง
- **SC-A03:** ทำการสั่งดาวน์โหลด (Export) รายงานข้อมูลการเข้าร่วมกิจกรรมเป็นไฟล์ (ถ้ามีการทดสอบ)

## 6. UAT Checklist (แบบฟอร์มตรวจสอบสั้นๆ สำหรับผู้ใช้)
ผู้ทดสอบใช้ Checklist นี้ระหว่างการลองใช้งาน หากมีข้อใดทำไม่ได้ให้ถือว่า "ไม่ผ่าน" (Fail):
- [ ] สามารถเข้าสู่ระบบด้วยบัญชีที่กำหนดได้
- [ ] เมนูแสดงผลตรงตามตำแหน่งหน้าที่ของตนเอง (ไม่เห็นเมนูของคนอื่น)
- [ ] ฟอร์มต่างๆ มีการแจ้งเตือนสีแดงหากกรอกข้อมูลผิดพลาด
- [ ] การสร้างข้อมูล (จองคลาส, สร้างคลาส) มีกล่องข้อความแจ้งเตือน "สำเร็จ" สีเขียว
- [ ] ตารางข้อมูลต่างๆ สามารถกดเปลี่ยนหน้า (Pagination) ได้

## 9. Acceptance Criteria (เกณฑ์การยอมรับ)
การทดสอบ UAT จะถือว่า **"สำเร็จ"** ก็ต่อเมื่อ:
1. ผู้ทดสอบสามารถทำ Test Scenarios ทั้งหมด (SC-M, SC-T, SC-A) ให้ผ่านได้อย่างน้อย 95%
2. ไม่มีปัญหาความผิดพลาดร้ายแรง (Blocker / Critical Bug) หลงเหลืออยู่ เช่น ระบบล่ม, หน้าขาว, ข้อมูลบันทึกผิดพลาด
3. หากมีปัญหาเล็กน้อย (Minor UI Issue เช่น สีปุ่ม, คำผิด) สามารถอนุมัติผ่านได้ โดยถือเป็นรายการที่ต้องแก้ไขในเวอร์ชันถัดไป (Backlog)

## 10. Sign-off Criteria (การลงนามส่งมอบ)
เมื่อเงื่อนไขการยอมรับผ่านเกณฑ์ ตัวแทนของผู้ทดสอบ (เช่น ผู้จัดการ หรือเจ้าของระบบ) จะต้องลงนามรับรองผล UAT เพื่อให้ทีมงานดำเนินการนำระบบขึ้นสู่สภาวะใช้งานจริง (Go-Live) ต่อไป
