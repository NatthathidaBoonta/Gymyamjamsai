# Implementation Recommendations & Risk Assessment

อ้างอิงจากการตรวจสอบเอกสาร Planning ทั้งหมดของระบบ **Gymyamjamsai** (ตั้งแต่ 01 ถึง 10) เอกสารฉบับนี้รวบรวมข้อสรุป จุดปรับปรุง และแนวทางที่จะถูกนำมาบังคับใช้จริงในกระบวนการ Implementation (ตั้งแต่ Phase 1 เป็นต้นไป)

---

## 1. การประยุกต์ใช้คำแนะนำ (Applied Recommendations)

เพื่อให้ระบบทำงานได้อย่างสมบูรณ์และลดความเสี่ยงระหว่างการพัฒนา ได้มีการตกลงนำคำแนะนำต่อไปนี้มาใช้งาน:

1. **Algorithm แจกตารางออกกำลังกาย (Phase 5):** 
   - ในเวอร์ชันแรก จะใช้กลไก **Static Template** (ดึงตารางสำเร็จรูปตามเป้าหมายของผู้ใช้และดัชนี BMI) แทนการเขียน Algorithm สุ่มท่าที่ซับซ้อน เพื่อให้สามารถทดสอบความถูกต้องได้ง่ายและ Launch ระบบได้เร็วขึ้น
2. **การป้องกันปัญหาแย่งจองคลาส / Race Condition (Phase 6):** 
   - ระบบจองกิจกรรม จะบังคับใช้ **Database Transaction Lock** เสมอ เพื่อป้องกันปัญหานักศึกษาหลายคนกดจองที่นั่งสุดท้ายในเสี้ยววินาทีเดียวกัน 
3. **Data Privacy / PDPA (Phase 8 & 9):** 
   - ในหน้าลงทะเบียน (Onboarding) จะมีการบังคับ Checkbox "ยินยอมให้ประมวลผลข้อมูลสุขภาพส่วนบุคคล"
   - ในหน้า Profile จะต้องมีเมนูให้ผู้ใช้สามารถ "ขอลบบัญชีตัวเอง (Right to be Forgotten)"
4. **ข้อจำกัดเรื่องบทลงโทษจากการจองคลาสแล้วไม่มา (No-show):** 
   - ระบบส่วนกลางจะทำหน้าที่เพียงเก็บสถิติ และ **แสดงข้อมูลการเช็คชื่อ (Attendance Data)** ให้ Trainer รับทราบเท่านั้น
   - **บทลงโทษ จะถูกปล่อยให้เป็นดุลยพินิจของ Trainer แต่ละท่านพิจารณาส่วนตัว** (ระบบจะไม่มีการแบน หรือตัดสิทธิ์การใช้งานใดๆ โดยอัตโนมัติ)

## 2. Checklist สรุปความพร้อมของระบบ (System Readiness)

1. **Requirement:** [✔️] ครบถ้วน (Functional / Non-functional)
2. **Role and Permission:** [✔️] ชัดเจน (Guest, Member, Trainer, Admin) 
3. **Workflow:** [✔️] ครอบคลุมวงจรชีวิตของการออกกำลังกายและการจองคลาส
4. **Database Design:** [✔️] ออกแบบโครงสร้างและระบุความสัมพันธ์สมบูรณ์พร้อมทำ Schema
5. **API Contract:** [✔️] ครอบคลุม Endpoints หลัก (REST API)
6. **Frontend Pages:** [✔️] จำแนกหน้าจอตาม Role และ Layout ของ MUI อย่างเป็นระบบ
7. **Dashboard and Report:** [✔️] ระบุตัวชี้วัด (KPIs), รูปแบบกราฟ และ SLA Alerts 
8. **Docker Architecture:** [✔️] ออกแบบ Multi-stage build รองรับ Railway และ On-premise
9. **Phase Plan:** [✔️] 15 Phases รองรับการพัฒนาตามลำดับ (Dependency)
10. **Acceptance Criteria:** [✔️] สามารถใช้วัดผลและตรวจรับงานได้จริง

## 3. จุดเสี่ยงที่ต้องเฝ้าระวังระหว่างการพัฒนา (Key Risks to Monitor)
- **File Upload Storage:** การเก็บรูปภาพไว้ใน Local Storage ของ Container บน Cloud อาจทำให้รูปโปรไฟล์หายเมื่อมีการ Deploy โค้ดใหม่ ในระหว่างการพัฒนา Phase ท้ายๆ อาจต้องพิจารณาเชื่อมต่อ Third-party (เช่น Cloudinary/S3)
- **Cron Job Server Load:** ระบบแจ้งเตือนรักษาวินัย (SLA Alerts) จะมีการคิวรี่ข้อมูลผู้ใช้จำนวนมาก ควรตั้งเวลารัน Cron Job ในช่วงที่คนใช้งานน้อย (เช่น 02:00 น.) 
- **Data Type & Indexing:** ใน Phase 2 (Database Schema) ต้องระมัดระวังการกำหนด Data Type (เช่น กำหนดน้ำหนักเป็น `DECIMAL(5,2)`) และควรสร้าง Index สำหรับฟิลด์ที่ใช้ Filter บ่อยๆ เพื่อป้องกันคอขวดของ Database
