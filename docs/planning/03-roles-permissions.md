# User Roles and Permissions: Gymyamjamsai

อ้างอิงจากระบบ Gymyamjamsai (ระบบติดตามพัฒนาการการออกกำลังกายออนไลน์) ในเอกสารก่อนหน้า ได้มีการกำหนดบทบาท (Roles) และสิทธิ์การเข้าถึง (Permissions) เพื่อให้การจัดการข้อมูลในระบบมีความปลอดภัย เป็นสัดส่วน และสอดคล้องกับ พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล (PDPA)

ในการวิเคราะห์นี้ **ได้มีการเสนอ Role "Guest" เพิ่มเติม** เพื่อให้สอดคล้องกับพฤติกรรมการใช้งานจริงของ Web Application 

## ตารางสรุป Role และ Permissions

| Role | คำอธิบายบทบาท | สิทธิ์ที่ทำได้ | หน้าจอที่เข้าถึงได้ | ข้อมูลที่มองเห็นได้ | ข้อจำกัดของ Role |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Guest** (ผู้เยี่ยมชม)<br><br>*(Role เสนอเพิ่มเติม)* | ผู้ใช้งานภายนอกทั่วไปที่เข้ามาที่เว็บไซต์ แต่ยังไม่ได้ทำการเข้าสู่ระบบ (Unauthenticated User) | • สมัครสมาชิก (Register)<br>• เข้าสู่ระบบ (Login)<br>• ดูรายการกิจกรรมเบื้องต้นเพื่อประกอบการตัดสินใจสมัคร | • Landing Page (แนะนำระบบ)<br>• หน้า Login / Register<br>• หน้า Activity Board (โหมด Public) | • ข้อมูลประชาสัมพันธ์ระบบ<br>• รายชื่อกิจกรรม, วันเวลา, และสถานะที่นั่ง (ว่าง/เต็ม) | • ไม่สามารถกดจอง/ลงทะเบียนกิจกรรมได้<br>• ไม่มีหน้า Dashboard ส่วนตัว<br>• ไม่เห็นข้อมูลเจาะลึกหรือรายชื่อผู้เข้าร่วม |

| **Admin** (ผู้ดูแลระบบ) | ผู้ดูแลระบบในภาพรวม จัดการข้อมูล Master Data และคอยควบคุมการทำงานของผู้ใช้งานทั้งหมด | • จัดการบัญชีผู้ใช้ (ระงับ, อนุมัติ, เปลี่ยน Role)<br>• จัดการคลังท่าออกกำลังกายหลัก<br>• ดูรายงานภาพรวมระบบ<br>• จัดการ/ลบกิจกรรมทั้งหมด (กรณีฉุกเฉิน) | • Admin Dashboard<br>• User Management<br>• Master Data Management<br>• Global Activity Management<br>• System Reports | • ข้อมูลบัญชีผู้ใช้ทั้งหมด (ยกเว้นรหัสผ่าน)<br>• กิจกรรมทุกประเภทในระบบ<br>• สถิติเชิงลึกระดับองค์กร (System Analytics)<br>• คลังท่าออกกำลังกาย | • **ไม่ควร/ไม่มีสิทธิ์** เข้าไปแก้ไขประวัติการออกกำลังกาย หรือตัวเลขน้ำหนักของ Member ด้วยตนเอง (เพื่อรักษา Data Integrity และ Privacy) |

### 💡 เหตุผลที่เสนอ Role "Guest" เพิ่มเติม
1. **User Acquisition:** Web Application ที่ดีควรเปิดโอกาสให้ผู้ที่สนใจ (แต่ยังลังเล) ได้เห็นภาพรวมของสิ่งที่จะได้รับ เช่น ให้เข้ามาดูหน้า Landing Page ที่สรุปฟีเจอร์เด่นๆ ของแอป หรือเห็นรายชื่อกิจกรรมออกกำลังกายที่น่าสนใจแบบคร่าวๆ เพื่อกระตุ้นให้อยากสมัครสมาชิก
2. **System Flow:** ป้องกันการนำข้อมูล Public (เช่น กิจกรรมบางประเภทที่ตั้งใจเปิดกว้างให้คนเห็นเยอะๆ) ไปล็อกเอาไว้หลังระบบ Login ทั้งหมด ซึ่งอาจลดโอกาสในการเข้าถึงของผู้ใช้หน้าใหม่

### 🔒 ข้อสังเกตด้าน Security & Privacy เพิ่มเติม
- **Data Privacy:** ข้อมูลสุขภาพถือเป็นข้อมูลส่วนบุคคลที่อ่อนไหว (Sensitive Data) ดังนั้นแม้แต่ Role อย่าง Admin ก็ควรถูกจำกัดสิทธิ์ให้ทำได้เพียง **ระงับบัญชี (Suspend)** แต่ไม่ควรมีสิทธิ์เข้าไปแก้ไข (Edit) ประวัติการบันทึกน้ำหนักหรือสัดส่วนของ Member เพื่อความโปร่งใสและปฏิบัติตามหลัก Privacy
- **Single vs Multiple Roles:** ในเฟสแรกของการพัฒนา แนะนำให้ล็อกโครงสร้างแบบ 1 Account ต่อ 1 Role (เช่น บัญชีนักศึกษา = Member เท่านั้น) เพื่อให้ง่ายต่อการพัฒนาและจัดการสิทธิ์ แต่ในระดับ Database Schema ควรออกแบบเผื่อความยืดหยุ่นไว้ด้วย
